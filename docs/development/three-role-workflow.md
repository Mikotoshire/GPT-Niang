# 项目三角色工作流

AI 生成的维护配置与文档，未经充分验证或独立人工审查；上游和第三方原作的许可、署名与权利归属保持不变。

## 范围与配置

仅本项目的实现、配置和文档修改使用此流程；普通问答、只读检查无需启动完整流程。协调者负责分派、上下文和验收，不直接编写应用运行时代码。角色子代理只向协调者返回状态，不递归启动本流程。

项目配置为 `.codex/config.toml`，角色定义为 `.codex/agents/gptniang_{planner,builder,verifier}.toml`。规划使用 `gpt-6-astra` / `high`；执行和独立验收默认使用 `gpt-6.1-sol` / `medium`。不改全局模型、沙箱、审批、网络、MCP 或安装生成的私有配置。

在仓库目录新建聊天并完成正常的项目信任流程后才能加载项目配置；未信任时可能忽略项目配置，不得静默改写全局信任设置。仓库外启动的当前聊天不会因写入文件自动热加载。激活后应实际检查 CLI 严格配置解析与角色发现，并报告实际采用的模型和推理强度。先核对实际调用的 CLI 版本，PATH 旧版和桌面捆绑版可能不同；支持选项的桌面 CLI 可用 `codex app-server --strict-config --print-startup-config` 检查严格解析。不要将不支持该选项的旧版 CLI、`features` 或 `debug` 命令失败误判为配置错误。解析通过不代表角色发现或实际模型调用已验证，仍须独立检查。配置和自然语言规则不构成可编程硬门禁；角色的只读指令也不是独立沙箱。不承诺完全执行或固定费用节省。

`max_concurrent_threads_per_session = 3` 是容量上限，用于避免保留的子线程阻塞下一阶段；工作仍串行，一次仅一个写入者。阶段完成后回收不需要的代理。容量错误最多一次有界重试，仍失败则报告阻塞；不得悄悄换模型或省掉独立验收。

## 交接与执行

1. 协调者保存原始用户需求与约束，确认分支、基线 SHA 和备份；向规划者提供必要代码位置。规划者只读，先取证，再给简短计划：原始需求、根因及证据/未知项、验收标准、基线 SHA、允许修改文件、回归风险和回滚方案。
2. 执行者按授权范围实现，在指定分支保持一个写入者。分派必须明确文件所有权；尊重其他人的修改，不覆盖用户工作。复用有意义的现有测试，补充能发现真实行为回归的测试，不以修改预期刷绿。保留回滚点；交接最终 SHA，或精确的未提交差异快照，以及实际检查命令、结果和局限。
3. 协调者启动全新上下文验收者（`fork_turns="none"`）。首轮只提供原始需求、约束、基线与最终 SHA/差异快照、允许检查的范围和环境；不提供执行者的根因或结论。验收者独立推导验收条件，质疑计划，检查实现与测试并复现关键情景；之后才交叉核对执行者证据。未提交树须保持稳定，否则重新绑定快照和验收。
4. 验收者返回 `PASS`、`CHANGES_NEEDED` 或 `BLOCKED`，附定位证据、实际命令/结果和未覆盖范围。仅可创建可丢弃的本地测试产物；不得编辑实现或测试预期，不得提交、合并或发布。缺少环境或独立上下文时明确 `BLOCKED`，不伪称独立验收完成。AI 验收不是独立人工审查。
5. 需要修改时由协调者将具体发现交给执行者，再启用新的独立验收上下文。用户真实反馈优先于历史测试结论；回调间隔或合成压力通过不能证明真实显示 FPS、输入体验或长期稳定性。

## 复用、升级与交付

已安装的 Superpowers `subagent-driven-development` 可用时，通过现有技能入口复用其全新上下文执行、规格审查和质量审查步骤，并遵守本项目模型分工和独立验收交接；不复制技能、不重复安装插件。不在时直接执行以上自包含步骤，不以缺少插件跳过验证。[Superpowers 来源](https://github.com/obra/superpowers)。

复杂的原生窗口、输入、性能、认证、安装、发布，或存在不确定性/重复失败时，先将 Sol 验收推理升到 `high`，仍需更强判断时启用新的 Astra `high` 上下文。自定义角色文件的固定模型与推理强度优先于分派参数，因此升级必须以 `fork_turns="none"` 启动全新的内置 `default`，或确认没有固定模型/推理配置的可用审查角色（例如本机 `code-reviewer`），显式传入 Sol / high 或 Astra / high；不得试图用分派参数覆盖固定为 medium 的自定义验收角色。该新代理须收到完整的验收者职责、原始用户需求、约束、验收标准及最终 SHA/稳定差异快照，并遵守首轮不接收执行者结论的独立验收规则。

当前聊天尚未加载自定义角色目录时，同样使用内置 `default` 或确认没有固定模型/推理配置的可用角色，加显式模型/推理参数和对应角色的完整职责作为临时替代；正式自定义角色在仓库内新建聊天后使用。用户已授权合理升级；协调者记录实际分派模型、推理强度、采用内置或未固定模型角色的原因和升级理由，不静默降级。同一方向两次修复未成功必须回到 Astra 重新规划，不进行第三次同类盲试。

交付报告应列出变更、实际验证、未覆盖场景、回滚点和实际角色模型。源码同步遵守 AGENTS.md 已授权的审查、隐私检查与普通推送策略；核对精确远端提交的 CI 终态，排队/运行中不算通过。制作可分发安装包、创建发行标签或发布 Release 仍需用户明确请求；本地备份标签和 CI 内部打包校验按既有维护授权执行。本次仅配置和文档变更不需要运行应用 GUI 测试。
